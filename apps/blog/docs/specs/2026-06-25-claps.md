# Spec: Sistema de Claps

**Data:** 2026-06-25
**Status:** superseded — persistência migrou para `apps/api`, ver `docs/specs/2026-06-25-api-claps-backend.md` (raiz). Este documento fica como histórico das decisões de produto/frontend (cookie, cap, UI), que continuam válidas; a seção 3 (modelo de dados) e o acesso direto a Postgres/Redis descritos aqui foram substituídos.
**Autor:** Beto

---

## Contexto

Hoje o blog é 100% estático (Astro, `output: 'static'`, sem adapter, deploy direto via Vercel + GitHub). Não existe nenhum estado compartilhado entre visitantes — a decisão registrada em `docs/context/decisions.md` é explícita: "sem banco de dados".

Um contador de claps por definição precisa de estado mutável e compartilhado (todo visitante vê e contribui para o mesmo número), então essa feature **não cabe** na arquitetura atual sem adicionar alguma forma de persistência. Isso é o trade-off central desta spec.

Alinhado com Beto: claps múltiplos por pessoa (estilo Medium, não um like binário), com cap por usuário, e ele topa adicionar uma dependência de KV serverless para viabilizar isso. Sem prazo definido.

---

## Objetivos

1. Botão de clap em cada post, com contador visível e compartilhado entre todos os visitantes.
2. Cada pessoa pode dar até N claps no mesmo post (estilo Medium), com limite reforçado no servidor.
3. Resto do site continua 100% estático/prerenderizado — só a rota de API do clap roda como serverless function.
4. Resiliente a abuso básico (clique automatizado, scripts) sem precisar de login.

## Fora do escopo

- Login/autenticação de usuário — identificação é anônima (cookie).
- Exibir lista de quem deu clap, ranking de posts, etc. — só o contador.
- Migrar outras partes do blog para SSR. Só a rota `/api/claps/[slug]` deixa de ser estática.
- Comentários ou qualquer outro sistema de estado — fica registrado como possível reuso futuro do mesmo Postgres/Redis, não implementado aqui.

---

## Opções consideradas

> Histórico: a opção A original (aprovada) era Upstash Redis gerenciado. Beto revisou três vezes depois da aprovação — primeiro para self-hostar Redis via Docker na própria VPS, depois para usar o Postgres que já roda nessa mesma VPS como ledger durável dos claps (com Redis ficando só com o rate limit), e por fim para parar de expor esse Postgres/Redis direto para a internet e colocar um backend NestJS (`apps/api`) na própria VPS mediando o acesso. **Esta última revisão é a versão final e está detalhada em `docs/specs/2026-06-25-api-claps-backend.md` (raiz)** — o texto abaixo (opções A/B/C) descreve a penúltima versão (Postgres+Redis acessados direto pela function do Vercel) e fica só como histórico de como se chegou até aqui.

### Opção A (recomendada): Postgres + Redis self-hosted, ambos na VPS do Beto (via Docker)

| Dimensão | Avaliação |
|---|---|
| Complexidade | Baixa — uma tabela no Postgres, sem ORM, sem migrations; rate limit é só `INCR`/`EXPIRE` no Redis |
| Custo | Zero — infra que o Beto já opera e já monitora/faz backup |
| Escalabilidade | Suficiente — é um contador, não um sistema transacional |
| Manutenção | Consolidada — não soma um terceiro serviço gerenciado; reaproveita Postgres e Redis que já existem |

**Pros:** zero dependência de serviço terceiro; Postgres já é a infra que o Beto confia para durabilidade/backup; Redis aplicado exatamente onde ele é o encaixe natural (estado efêmero de rate limit, com TTL); sem custo incremental.
**Contras:** é uma exceção mais explícita à regra "sem banco de dados" do que um KV puro, já que passa a existir uma tabela relacional de fato (ver seção de impacto abaixo); exige expor Postgres/Redis da VPS para as functions do Vercel alcançarem (rede pública — ver riscos).

### Opção B: Upstash Redis (KV serverless gerenciado) — descartada

**Pros:** zero infra própria para manter.
**Contras:** dependência de um serviço terceiro quando o Beto já opera Postgres e Redis na própria VPS — preferiu consolidar em infra que já mantém em vez de somar uma conta externa.

### Opção C: Zero backend (contador só em `localStorage`)

**Pros:** nenhuma dependência nova, mantém a decisão original intacta.
**Contras:** **não atende ao requisito** — cada visitante veria só a própria contagem local, nunca o total agregado de todo mundo. Rejeitada: não é um "contador de curtidas" de fato, é só uma preferência pessoal salva no navegador.

**Decisão:** Opção A (versão self-hosted Postgres + Redis).

## Decisões técnicas

### 1. Astro passa a ter uma rota não-estática

Astro 5 com `output: 'static'` (padrão atual, sem adapter) não permite endpoints dinâmicos no Vercel. Precisa:

```bash
pnpm add @astrojs/vercel --filter @nico.dev/blog
```

```js
// astro.config.mjs
import vercel from '@astrojs/vercel';

export default defineConfig({
  output: 'static', // tudo continua estático por padrão
  adapter: vercel(),
  // ...resto inalterado
});
```

Só a rota de claps opta por renderização sob demanda:

```ts
// src/pages/api/claps/[slug].ts
export const prerender = false;
```

Todas as outras páginas (posts, home, categorias) continuam pré-renderizadas em build — zero impacto de performance ou SEO nelas.

### 2. Identificação anônima do visitante

Cookie `nico_uid` (UUID v4), `SameSite=Lax`, validade 1 ano, criado no primeiro clap. Não é `httpOnly` porque o island cliente precisa lê-lo para mostrar "você já deu N claps aqui". O cap real, porém, é sempre validado no servidor — um usuário que limpa o cookie ganha um novo `uid` e, na prática, um novo orçamento de claps. É uma limitação conhecida e aceitável para uma feature de engajamento leve (não é antifraude financeiro).

### 3. Modelo de dados — **superseded, ver `docs/specs/2026-06-25-api-claps-backend.md` (raiz)**

> O texto abaixo descreve a versão em que o blog falava direto com Postgres/Redis. Na versão final, esse modelo de dados (agora via Prisma) e o acesso a Postgres/Redis vivem em `apps/api`; o blog só consome `GET/POST /claps/:slug` dessa API por HTTP. Mantido aqui por histórico.

**Postgres** (ledger durável dos claps — fonte da verdade):

```sql
CREATE TABLE claps (
  slug TEXT NOT NULL,
  uid UUID NOT NULL,
  count INTEGER NOT NULL DEFAULT 0,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (slug, uid)
);
```

Total do post = `SUM(count) WHERE slug = ?`, calculado em tempo de leitura (volume de linhas por post — visitantes únicos que deram clap — é pequeno demais para justificar manter uma coluna de total separada). Upsert atômico via `INSERT ... ON CONFLICT (slug, uid) DO UPDATE SET count = LEAST(count + amount, 50)` cobre a concorrência.

**Redis** (rate limit, efêmero — não guarda claps):

```
ratelimit:claps:{ip} → INCR + EXPIRE 10s
```

Sem TTL na tabela de claps — claps são permanentes, assim como os posts (consistente com a regra de posts nunca serem deletados). TTL só existe no lado do rate limit, que é descartável por natureza — daí ficar em Redis e não em Postgres.

### 4. Endpoints

`GET /api/claps/[slug]` → `{ total: number, userClaps: number }` (lê `uid` do cookie; se não existir, `userClaps: 0`).

`POST /api/claps/[slug]` com body `{ amount: number }` (1–5, batch de cliques) →
- Valida que `userClaps + amount <= 50`, ajusta `amount` se exceder o cap.
- Faz upsert capado na tabela `claps` (Postgres).
- Retorna `{ total, userClaps }` atualizados.
- 404 se o slug não existir na content collection.

### 5. Anti-abuso

- Cap rígido de 50 claps/usuário/post, reforçado no servidor (não confia só no client) — agora reforçado em `apps/api`, não mais na própria rota Astro.
- Rate limit por IP — **superseded**: a versão final usa `@nestjs/throttler` (storage Redis) dentro de `apps/api`, não mais `INCR`/`EXPIRE` manual na rota Astro. Mesma política (20 req / 10s por IP). Ver `docs/specs/2026-06-25-api-claps-backend.md`.
- Debounce no client: cliques rápidos acumulam localmente e disparam um único `POST` a cada ~600ms de inatividade, em vez de uma requisição por clique. (Isso não muda — é puramente client-side.)

### 6. Frontend

Novo React island `src/components/ClapButton.tsx` (`client:visible`):
- No mount, faz `GET` para preencher `total` e `userClaps` reais.
- Otimista: cada clique incrementa o estado local na hora; o `POST` debounced confirma em background.
- Ao atingir o cap, desabilita novos incrementos visualmente mas mantém o contador visível.
- Inserido no footer de `[slug].astro` (layout default) e `ImmersivePostLayout.astro` — os dois pontos onde o conteúdo do post termina hoje.

### 7. Posts arquivados

**Decisão (Beto, 2026-06-25):** posts com `status: archived` permitem clap normalmente, sem modo só-leitura — mesmo comportamento de um post `published`. A rota de claps não filtra por status ao validar a existência do slug.

## Impacto na decisão "sem banco de dados"

`docs/context/decisions.md` registrava: *"Astro (build estático) — sem Next.js, sem NestJS, sem banco de dados"*. Esta spec evoluiu quatro vezes desde a primeira aprovação:

1. Versão original aprovada: Upstash Redis (KV serverless gerenciado).
2. Beto decidiu self-hostar Redis via Docker na própria VPS, removendo a dependência de um serviço terceiro.
3. Beto identificou que já opera um container Postgres independente na mesma VPS e perguntou se seria mais adequado para os claps. Postgres passou a ser o ledger durável dos claps, Redis ficou restrito ao rate limit.
4. **Versão final:** Beto perguntou se fazia sentido criar um backend de verdade (NestJS) na VPS para mediar esse acesso, em vez do blog falar direto com Postgres/Redis. **Decisão: sim** — ver `docs/specs/2026-06-25-api-claps-backend.md` (raiz).

O resultado prático para o blog é, na verdade, **mais alinhado** com "sem banco de dados" do que qualquer versão anterior: `apps/blog` não tem nenhum cliente de Postgres/Redis, nenhuma connection string de banco, nenhuma query SQL. A única coisa que ele faz é uma chamada HTTP para `apps/api` (um serviço externo ao blog, assim como seria uma API de terceiros) — `lib/claps.ts` é só um `fetch`. O banco de dados de fato existe, mas pertence a `apps/api`, não ao blog. Por isso a linha em `decisions.md` deste app não fala mais de Postgres/Redis self-hosted, e sim de "consome `apps/api` via HTTP".

**Aplicado em 2026-06-25:** `decisions.md` deste app atualizado para a versão final (consumo via HTTP de `apps/api`); a exceção "Postgres+Redis self-hosted" anterior foi substituída.

## Critérios de aceite

- [ ] Clicar no botão incrementa o contador na tela imediatamente (otimista), sem esperar a rede.
- [ ] Recarregar a página mostra o total persistido corretamente (vindo do Postgres).
- [ ] Um mesmo `uid` não consegue passar de 50 claps em um post — validado no servidor mesmo se o client for manipulado.
- [ ] As demais páginas do site continuam sendo geradas estaticamente no build (`astro build` não muda o output das páginas que não são a rota de claps).
- [ ] `GET /api/claps/[slug]` retorna 404 para slug inexistente.
- [ ] Variáveis de ambiente documentadas em `.env.example` e configuradas no projeto Vercel.

## Dependências e riscos

> **Superseded** — riscos de Postgres/Redis expostos e de pool de conexões serverless deixaram de existir nesta versão final, porque o blog não fala mais direto com banco de dados. Ver `docs/specs/2026-06-25-api-claps-backend.md` (raiz) para os riscos da versão atual (ponto único de falha na VPS, deploy manual, etc.). Tabela abaixo mantida como histórico.

| Item | Risco | Mitigação |
|---|---|---|
| `@astrojs/vercel` | Pode exigir ajuste de versão para compatibilidade com Astro 5 | Checar compatibilidade na instalação antes de seguir |
| ~~Postgres/Redis expostos da VPS para a internet pública~~ | ~~Vercel functions não têm IP fixo por padrão; porta aberta sem proteção é risco de acesso indevido~~ | **Resolvido na versão final** — Postgres/Redis ficam só na rede interna Docker de `apps/api`, nunca expostos |
| ~~Conexões TCP persistentes em ambiente serverless~~ | ~~Cada cold start do Vercel pode abrir uma conexão nova~~ | **Resolvido na versão final** — quem mantém pool de conexões é `apps/api`, um processo Node persistente, não o blog |
| Cookie `uid` resetável | Usuário pode limpar cookies e "ganhar" novo orçamento de claps | Aceitável para MVP; documentado como limitação conhecida |
| Rota não-estática no Vercel | Cold start ocasional na function | Latência adicional até a VPS via HTTPS; aceitável para o volume de um blog pessoal |
| Dependência de `apps/api` estar no ar | Se a api da VPS cair, claps para de funcionar | Ver riscos detalhados em `docs/specs/2026-06-25-api-claps-backend.md` |
