# Spec: Wake Lock durante treino ativo

**Status:** approved
**Data:** 2026-06-04
**Autor:** planner

---

## Problema

O metrônomo é usado em sessões de treino ativas, frequentemente em dispositivos móveis. O sistema operacional pode desligar a tela após inatividade de toque, interrompendo a sessão silenciosamente. O usuário perde o feedback visual do metrônomo sem perceber que isso aconteceu.

---

## Cenários de Usuário

- **P1 (crítico):** Como músico em treino ativo, quero que a tela permaneça acesa enquanto o metrônomo estiver tocando, para não perder o feedback visual.
- **P2 (importante):** Como usuário que alterna entre abas, quero que o Wake Lock seja reativado automaticamente ao retornar à aba do metrônomo, para não precisar interagir com a tela.
- **P3 (nice-to-have):** Como desenvolvedor, quero um hook `useWakeLock` desacoplado e reutilizável, para poder aplicá-lo em outras partes da aplicação no futuro.

---

## Requisitos Funcionais

- **FR-001:** O hook `useWakeLock` deve aceitar um parâmetro `isActive: boolean` e solicitar `navigator.wakeLock.request('screen')` quando `isActive` mudar para `true`.
- **FR-002:** Quando `isActive` mudar para `false`, o Wake Lock deve ser liberado imediatamente via `WakeLockSentinel.release()`.
- **FR-003:** Ao detectar `visibilitychange` com `document.visibilityState === 'visible'` e `isActive === true`, o hook deve reativar o Wake Lock automaticamente.
- **FR-004:** Apenas um `WakeLockSentinel` deve estar ativo por vez; qualquer sentinel anterior deve ser liberado antes de solicitar um novo.
- **FR-005:** Em navegadores sem suporte à Wake Lock API (`'wakeLock' in navigator === false`), o hook deve silenciosamente não fazer nada, sem lançar erros.
- **FR-006:** Erros de `wakeLock.request()` (permissão negada, economia de bateria, release automático pelo SO) devem ser capturados e logados em `console.warn`, sem propagar exceção para o componente.
- **FR-007:** O hook deve ser compatível com React Strict Mode: efeitos que montam/desmontam duas vezes não devem deixar sentinels órfãos nem listeners duplicados.
- **FR-008:** Todos os event listeners (`visibilitychange`, evento `release` do sentinel) devem ser removidos no cleanup do `useEffect`.
- **FR-009:** O hook deve ser integrado em `useMetronome` passando o `isPlaying` como `isActive`, sem expor detalhes de Wake Lock na interface pública `MetronomeState`/`MetronomeActions`.

---

## Critérios de Sucesso

- [ ] Com metrônomo tocando em dispositivo móvel, a tela permanece acesa por pelo menos 5 minutos sem toque.
- [ ] Ao pausar o metrônomo, o Wake Lock é liberado e o SO retoma o comportamento normal de desligar a tela.
- [ ] Ao trocar de aba e voltar com o metrônomo ativo, o Wake Lock é readquirido sem ação do usuário.
- [ ] Em navegador sem suporte (Firefox ≤ 90, Safari ≤ 16.3), a aplicação funciona normalmente sem erro no console.
- [ ] Modo de economia de bateria ativado: erro é capturado, logado como `warn`, metrônomo continua funcionando.
- [ ] Nenhum memory leak detectável após 10 ciclos de play/pause no React DevTools Profiler.

---

## Fora do Escopo

- Exibir estado do Wake Lock (ativo/inativo/não suportado) na UI.
- Controle manual pelo usuário para ativar/desativar Wake Lock.
- Suporte a outros tipos de lock além de `'screen'`.
- Persistência de preferência de Wake Lock entre sessões.

---

## Riscos e Premissas

- **Premissa:** O `isPlaying` de `useMetronome` é a fonte de verdade para "treino ativo" — o hook não precisa de sinal adicional.
- **Premissa:** A aplicação roda em contexto HTTPS (obrigatório pela Wake Lock API).
- **Risco:** React Strict Mode chama efeitos duas vezes em desenvolvimento → Mitigação: cleanup do `useEffect` deve liberar sentinel e remover listener antes da remontagem; lógica de reativação no `visibilitychange` já reaquire naturalmente.
- **Risco:** O SO pode liberar o Wake Lock proativamente (bateria crítica, chamada recebida) → Mitigação: listener no evento `release` do sentinel detecta liberação e permite reaquirição no próximo `visibilitychange`.
- **Risco:** `wakeLock.request()` é assíncrono; múltiplas chamadas rápidas (toggle play/pause) podem criar race condition → Mitigação: verificar se sentinel anterior ainda está ativo antes de solicitar novo; usar flag `isAcquiring` via ref para serializar.
